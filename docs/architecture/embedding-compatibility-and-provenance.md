# Lina Architecture — Embedding Compatibility, Provenance, and Multi-Device Search

**Status:** Architecture Specification (Approved Rules & Proposed Implementation Contracts)  
**Scope:** Vector space compatibility invariants, provenance metadata contract in published manifests, Companion provider/model inheritance, query embedding mechanics, fail-safe degradation to local text search, decoupling of embeddings from AI analysis, and persistent device-local temporary Companion embedding overlays.

---

## 1. Current Confirmed Behavior

In the current Lina codebase (`v0.2.3` / `v0.2.4-dev`):

1. **Published Artifact Manifest (`.lina/index/manifest.json`):**
   When the Producer saves the search index and vector embeddings, `.lina/index/manifest.json` records:
   - `provider` (string, e.g. `"ollama"`, `"mistral"`, `"openrouter"`);
   - `model` (string, e.g. `"all-minilm"`, `"mistral-embed"`);
   - `dimensions` (integer, e.g. `384`);
   - `formatVersion` (integer);
   - `producerDeviceId` (UUID string);
   - `producerEpoch` (integer);
   - `generatedAt` (ISO 8601 timestamp);
   - `embeddings`: sub-object containing `enabled`, `totalEmbeddings`, `publicationId`, and `sourceTotalChunks`.
2. **Derived Binary Vector Manifest (`.lina/index/embeddings.binary.manifest.json`):**
   Compiled by `BinaryWorker` on Desktop Producer, recording:
   - `generationId` and `sourcePublicationId` (matching `publicationId` of the canonical manifest);
   - `metadataDigest` and `vectorsDigest` (cryptographic SHA-256 digests);
   - `recordCount`, `dimensions`, `provider`, `model`, `provenance`.
3. **Runtime Compatibility Validation (`src/search/linaSearchView.ts`, `src/search/semanticSearchModal.ts`):**
   When executing semantic search, the search layer validates:
   - `indexProvider === settingsProvider` (case-insensitive);
   - `indexModel === settingsModel`;
   - `runtimeIndex.sourceIdentity.prefixMode === nextIdentity.prefixMode`;
   - `queryEmbedding.length === expectedDimension`.
   If any check fails, semantic search halts and displays an error message.
4. **Companion Generation Gating (`src/capabilities/deviceCapabilities.ts`, `src/companion/companionCapability.ts`):**
   - `canGenerateEmbeddings` resolves to `false` when `deviceRole === "companion"`.
   - Background embedding schedulers (`EmbeddingScheduler`) and worker pipelines (`EmbeddingWorker`) are deactivated on Companion devices.
   - Manual generation commands fail-fast if invoked on a Companion.

## 2. Confirmed Gaps

1. **Uncoordinated UI Configuration on Companion:**
   The Settings view on Companion currently displays editable dropdowns for the Embedding Provider and Model. A user who configures a provider or model different from the Producer's published index encounters immediate errors upon searching.
2. **Query Vector Generation Mechanics on Mobile:**
   To perform semantic search, the Companion must compute an embedding vector for the user's search query (`generateSingleEmbedding`) matching the exact model of the index. If the Producer used a local desktop Ollama instance (`http://localhost:11434`), a mobile Companion cannot connect to `localhost:11434` without specialized network routing, causing query generation to fail with a generic error.
3. **Outdated Absolute Dogma:**
   The historical roadmap rule *"Mobile never creates embeddings"* conflicts with approved functional requirements where mobile users need visibility over missing embeddings and the ability to trigger local creation when needed.
4. **Absence of Temporary Companion Overlay:**
   When a note is created or edited on Companion, it cannot be searched semantically until the Desktop Producer syncs updated embeddings. There is currently no mechanism for Companion to maintain temporary local embeddings without attempting to mutate canonical shared files.

## 3. Approved Product Rules

The following functional rules are formally approved:

1. **Mathematical Incommensurability:** Vectors generated by different models or dimensionalities occupy fundamentally distinct coordinate spaces. Distance metrics across different models produce meaningless noise.
2. **Contract Inheritance & Zero Silent Fallback:** The Companion must inherit the vector contract (provider, model, dimensions, prefixing) established by the Producer's published artifacts in `.lina/index/manifest.json`. Under no circumstances will Lina silently fall back to an alternate embedding model or provider.
3. **Graceful Textual Degradation:** If the inherited embedding model is unreachable or unavailable on Companion, **semantic search is explicitly and gracefully suspended with an informative status notice**. Local text search remains available whenever a usable text index or local search state exists.
4. **Decoupling of Embeddings from AI Analysis:** The provider and model used for **Vector Embeddings** must remain strictly decoupled from the provider and model configured for **AI Note Analysis** (`/ask`, `/tags`, `/yaml`). A user may search notes embedded via desktop Ollama while analyzing notes via Claude or OpenRouter on mobile.
5. **Temporary Companion Embedding Cache (Approved Decision):**
   - Embeddings created on a Companion are **strictly temporary and stored in a persistent, device-local cache excluded from vault synchronization**.
   - They serve exclusively to make newly created or modified notes searchable on that device before the Producer updates and synchronizes canonical artifacts.
   - They are **never published** by the Companion as canonical artifacts, **never synchronized** to other devices, and **never written** into Producer-owned shared files (`.lina/index/embeddings.jsonl`, `.lina/index/embeddings.vectors.f32`, etc.).
   - They do not alter Producer ownership, do not transform the Companion into a Producer, and must strictly respect the active Exclusion Policy.
   - They are retained only until the Producer publishes, and external synchronization delivers, canonical embeddings that correctly and completely cover the same note versions.
   - Removable exclusively through deterministic cache reconciliation; **the Producer remains the sole authority for canonical shared embeddings.**
   - The concrete storage API and physical location are an implementation detail subject to a technical spike and audit in Phase 0.4.x.

## 4. Proposed Implementation Contracts (Phases 0.3.x & 0.4.x)

### 4.1 Vector Contract & Extended Metadata in Manifest (`.lina/index/manifest.json`) — Planned for 0.3.x
To ensure unambiguous contract transmission across devices, the published artifact manifest is proposed to formalize the vector specification and exclusion policy fingerprint:

```json
{
  "formatVersion": 2,
  "producerDeviceId": "e9a7c3b2-7b12-4c28-8d4e-123456789abc",
  "producerEpoch": 2,
  "generatedAt": "2026-09-04T12:00:00.000Z",
  "exclusionPolicyRevision": 1,
  "exclusionPolicyHash": "d41d8cd98f00b204e9800998ecf8427e",
  "vectorContract": {
    "provider": "ollama",
    "model": "all-minilm",
    "dimensions": 384,
    "prefixMode": "none"
  }
}
```

> [!NOTE]
> The exact `exclusionPolicyHash` tracking mechanism is proposed for Phase 0.3.x in [Exclusion Policy and Artifact Invalidation](exclusion-policy-and-artifact-invalidation.md). Until this contract is implemented and validated, devices must retain conservative behavior: absence of proven policy compatibility prevents cache supersession.

### 4.2 Companion Settings UI Locking — Planned for 0.3.x
In the Companion Settings tab:
- **Embedding Provider & Model:** Proposed to be rendered in read-only mode, labelled *"Inherited from Producer"*.
- **Connection Details:** Proposed to allow configuring local connection credentials or endpoints needed by the inherited model (e.g. entering a LAN IP endpoint for Ollama, or entering a local API key in `app.secretStorage` for external providers).

### 4.3 Temporary Companion Cache Entry Schema — Planned for 0.4.x
Because note content in Lina is partitioned into text chunks (`Chunk` in `src/index/chunker.ts`), each entry in the Companion's local persistent cache is planned to record sufficient chunk-level metadata to prove equivalence and validity:

```json
{
  "schemaVersion": 1,
  "path": "Work/Project-Alpha.md",
  "contentHash": "a4f8c2b1",
  "vectorContractId": "ollama:all-minilm:384:none",
  "provider": "ollama",
  "model": "all-minilm",
  "dimensions": 384,
  "prefixMode": "none",
  "exclusionPolicyRevision": 1,
  "exclusionPolicyHash": "d41d8cd98f00b204e9800998ecf8427e",
  "createdAt": "2026-09-04T14:30:00.000Z",
  "chunkIndex": 0,
  "chunkId": "Work/Project-Alpha.md::0",
  "chunkTextHash": "f1e2d3c4",
  "embedding": [0.0123, -0.0456, "..."]
}
```

- `chunkId` uses the canonical Lina chunk separator `${path}::${chunkIndex}`.
- `createdAt` is retained strictly for diagnostics, telemetry, and local cache retention policies. **It is never used as proof of equivalence.**

## 5. Recognition Contract & Equivalence Proof

Timestamps alone are fundamentally unsafe for cache supersession because of device clock drift, timezone variations, and out-of-order external file synchronization. Furthermore, the mere presence of a note path or note-level content hash in canonical artifacts does not prove that all embedding vectors required for that note are present, valid, and loadable.

### 5.1 The Core Invariant
A temporary Companion embedding entry is considered safely superseded and eligible for removal if and only if the following invariant holds:

```text
same note version
+ complete canonical chunk/vector coverage
+ same vector contract
+ valid active exclusion policy
+ completely validated artifact generation
= temporary cache entry may be removed
```

### 5.2 Cumulative Equivalence Conditions
Cache removal requires verification of all five of the following conditions:

1. **Same Note Identity and Content Revision:**
   Canonical artifacts contain an entry for the exact normalized note path (`obsidian.normalizePath(entry.path)`) with a `contentHash` (`hashContent()`) that matches the temporary cache entry identically.
2. **Complete Usable Vector Coverage:**
   The canonical generation must contain complete, usable vector coverage for the exact set of chunks derived from that note content version. Verification requires:
   - Derivation of the exact canonical chunk set for that note version (matching chunk count, stable chunk identifiers `${path}::${chunkIndex}`, and chunk text hashes);
   - A valid embedding vector entry present for every required chunk of that note;
   - Exact agreement between JSONL metadata (`embeddings.jsonl` or `embeddings.meta.jsonl`) and binary vector storage (`embeddings.vectors.f32`), verifying vector offsets and counts;
   - Successful loading and runtime validation of those vectors into memory (e.g. into `Float32Array` buffers);
   - Absolute absence of partial, truncated, or mixed-generation chunk data for that note.
3. **Matching Vector Contract:**
   The canonical `.lina/index/manifest.json` declares the identical provider, model, dimensions, and `prefixMode` (or identical deterministic vector-contract identifier).
4. **Compatible Exclusion Policy Verification:**
   - A monotonic revision number alone proves ordering, NOT semantic compatibility. A higher revision could represent a more restrictive or less restrictive policy.
   - The canonical artifact generation must identify the exact exclusion-policy fingerprint/hash (`exclusionPolicyHash`) under which it was built;
   - That fingerprint must be compatible with the currently active Producer-owned policy (preferring an exact match unless a formally proven compatibility rule exists);
   - The active policy must be evaluated again for the note at reconciliation time and confirm the note remains eligible;
   - If the note becomes excluded under the active policy, it is purged promptly regardless of generation ordering or revision numbers;
   - Because the exact policy-hash design remains proposed for Phase 0.3.x, conservative behavior must be retained: without proof of policy compatibility, temporary entries must not be purged based on numeric revision comparisons alone (`policyRevision >= cachedPolicyRevision` is strictly rejected as proof of eligibility).
5. **Completely Received & Validated Generation:**
   The canonical generation has completed the full synchronization safety handshake (§6).

Only when all applicable conditions are satisfied may the Companion remove the corresponding temporary cache entry.

### 5.3 Reconciliation Granularity
Because a note is partitioned into multiple chunks, cache storage and reconciliation must operate at the appropriate granularity:
- If the temporary cache stores entries per chunk (or a note-level chunk collection), the temporary representation for a note must **never be removed merely because a single canonical chunk is available**.
- The entire set of chunks derived from that note version must be confirmed present and valid in the canonical index before any temporary cache entries for that note version are retired.
- If canonical coverage for a note is partial, missing chunks, or corrupted, the temporary representations for that note must remain active to prevent search degradation or missing query matches.

## 6. Synchronization Safety & Validation Handshake

External sync engines (Obsidian Sync, Syncthing, iCloud, Dropbox) deliver files individually, non-atomically, and in arbitrary order. A device may receive `.lina/index/manifest.json` minutes before `chunks.jsonl`, or receive `embeddings.vectors.f32` while `notes.json` is still syncing.

Receiving a newer file timestamp or manifest does not prove that the generation is usable.

### Multi-Step Validation Handshake on Companion:
1. **Manifest Integrity:** Read `.lina/index/manifest.json`. Verify valid JSON shape, matching schema version, valid provenance (`producerDeviceId`, `producerEpoch`), and compatible `exclusionPolicyHash`.
2. **File Existence & Size Check:** Confirm that all canonical files declared in the manifest (`notes.json`, `chunks.jsonl`, and `embeddings.jsonl` or `embeddings.vectors.f32`) exist locally on disk and match expected non-zero sizes.
3. **Digest & Publication Handshake:**
   - If using binary acceleration (`embeddings.binary.manifest.json`), verify that `sourcePublicationId` matches `manifest.embeddings.publicationId`.
   - Verify SHA-256 digests (`vectorsDigest`, `metadataDigest`) against the actual bytes of `embeddings.vectors.f32` and `embeddings.meta.jsonl` on disk.
4. **Internal Count & Vector Consistency:**
   - Verify that `manifest.totalNotes === notes.length` and `manifest.totalChunks === chunks.length`.
   - Verify that the declared vector count matches binary payload byte length (`recordCount * dimensions * 4`).
   - Confirm complete alignment between JSONL metadata records and binary vector ordinals with no orphaned, missing, or mixed-generation vectors.
5. **Atomic State Transition:** Only when steps 1–4 succeed is the canonical generation promoted to `valid` in `CompanionArtifactConsumptionState`. If any check fails, the canonical generation is treated as `partial` or `stale`, and the temporary Companion cache remains active.

## 7. Cache Reconciliation Rules

When reconciling the temporary local cache against the vault and synchronized artifacts, the Companion executes the following deterministic rules:

### Case 1: Canonical Equivalent Received
- **Condition:** All 5 equivalence conditions (§5.2) are met: same note version, complete canonical chunk/vector coverage, matching vector contract, compatible exclusion-policy fingerprint, and fully validated generation.
- **Action:** Query execution delegates to the canonical vector index; the matching temporary cache entries for that note are removed from the local store; duplicate results are completely prevented.

### Case 2: Canonical Generation is Newer but Covers Different Content or Incomplete Chunks
- **Condition:** A newer canonical generation ($G_{new} > G_{old}$) arrives via sync, but its `contentHash` for the note differs from the current local note or from the temporary entry, or it does not contain complete usable vector coverage for all chunks of that content revision (e.g. the note was edited on Companion after the Producer started generating, or sync is still in flight).
- **Action:** The temporary entry is **retained**. It represents the newer local content or complete vector set that the Producer has not yet fully published and delivered. Canonical vectors are used for unchanged notes; the temporary entry is used for the modified note.

### Case 3: Note or Chunks Absent from Canonical Artifacts
- **Condition:** The canonical generation validates, but the note does not appear in `notes.json`, or some required chunks lack canonical vector entries.
- **Action:** Do not delete the temporary entry. Distinguish between:
  - *Pending Processing:* Note was created on Companion and has not yet been indexed by Producer (retain temporary entry);
  - *Partial Synchronization:* Vault note file or chunk embeddings have not yet synced completely (retain temporary entry);
  - *Deletion / Exclusion:* Note was deleted locally or matches exclusions (see Case 4).

### Case 4: Note Becomes Excluded or Deleted Locally
- **Condition:** The active Producer-owned exclusion policy excludes the note path/content (evaluated dynamically at query or reconciliation time), or the markdown note no longer exists locally in the vault.
- **Action:** Remove its temporary embedding promptly from the local cache, regardless of embedding-generation ordering or revision numbers. Ensure it cannot appear in text, semantic, hybrid, or delta search results, and block any transmission to AI providers.

### Case 5: Vector Contract Changes on Producer
- **Condition:** Producer republishes `.lina/index/manifest.json` with a different provider, model, dimensions, or prefix mode.
- **Action:** Mark all temporary cache entries generated under the old contract as `incompatible`. Do not compare, score, or merge them with new canonical vectors. Incompatible entries are pruned or scheduled for re-embedding only through explicitly authorized Companion flows using the new inherited contract.

### Case 6: Application Restart or Interrupted Cleanup
- **Condition:** The Obsidian app is closed or crashed during search, embedding generation, or cleanup.
- **Action:** The persistent device-local cache survives restart. On startup, cleanup is executed as an **idempotent sweep**: no temporary entry is removed unless its corresponding canonical equivalent is currently loaded and verified in memory. Interruption cannot leave a note without representation.

## 8. Search Behavior & Result Fusion

The Companion search layer executes according to the following fusion pipeline:

```text
┌────────────────────────────────────────────────────────┐
│         VALIDATED CANONICAL PRODUCER EMBEDDINGS        │
│         (from synchronized shared index artifacts)     │
└───────────────────────────┬────────────────────────────┘
                            │
                            │ (for notes where canonical contentHash === vault note)
                            ▼
                  ┌────────────────────┐
                  │ RESULT DEDUPLICATOR│ ◄─── (Canonical wins on proven equivalence)
                  └────────────────────┘
                            ▲
                            │ (for notes with newer local edits or pending Producer sync)
                            │
┌───────────────────────────┴────────────────────────────┐
│      ELIGIBLE TEMPORARY LOCAL COMPANION EMBEDDINGS     │
│      (from unsynchronized device-local cache)          │
└────────────────────────────────────────────────────────┘
                            │
                            ▼
         [FUSED SEMANTIC / HYBRID RANKED RESULTS]
```

- **Precedence:** Canonical data wins only when equivalence with the active note version is proven. If a note has local modifications, its valid temporary local embedding supersedes stale canonical vectors.
- **Strict Device Scope:** The temporary cache is never exposed to or read by any other device.

## 9. Open Technical Decisions & Storage Audit

### 9.1 Physical Storage Mechanism for Device-Local Cache
The product decision confirms a **persistent device-local cache excluded from vault synchronization**. The concrete storage API and physical location remain an implementation detail to be finalized via a dedicated technical spike during Phase 0.4.x:

| Candidate Mechanism | Storage Boundary | Assessment & Trade-offs | Status |
| :--- | :--- | :--- | :--- |
| **Option A: Host IndexedDB (`window.indexedDB`)** | Webview / Host Application Storage | Located in the browser/WebView host storage outside the vault filesystem; not directly handled as a vault file by vault synchronization tools (Obsidian Sync, iCloud, Syncthing, Dropbox). Supports large binary/typed-array payloads (`Float32Array`) and structured indexing. Browser/WebView storage carries its own lifecycle and eviction risks that must be audited. | **Leading Candidate to Investigate** |
| **Option B: `app.loadLocalStorage` / `app.saveLocalStorage`** | Obsidian Host Key-Value Store | Official Obsidian API; outside vault filesystem. Backed by `localStorage` with a strict quota limit (typically ~5MB total across all keys), which is easily exceeded by vector arrays (e.g. 1000 chunks × 384 dims × 4 bytes = 1.5MB raw floats alone). | Unviable for vector payloads; retained only for scalar device identity |
| **Option C: Dedicated Device-Scoped File (`.lina/devices/<deviceId>/...`)** | Vault Filesystem | Managed via `app.vault.adapter`. Resides inside the vault filesystem tree; external sync tools (Syncthing, iCloud) may sync it across devices unless specifically configured with ignore rules, violating the non-synchronizable boundary requirement. | **Rejected** (resides inside vault tree) |

#### Technical Spike & Implementation Audit Requirements for Option A (IndexedDB):
Before committing to IndexedDB in Phase 0.4.x implementation, a spike must validate:
1. **Cross-Platform WebView Support & Behavior:** Consistent behavior across Obsidian Desktop (Chromium/Electron), Android WebView (Blink), and iOS WebView (WKWebView).
2. **Namespace Isolation:** Strict partitioning between vaults and plugin instances (e.g. database name keyed by vault ID or hashed vault path) to prevent cross-vault collisions or data leaks.
3. **Plugin & Vault Lifecycle:** Behavior during plugin disable, uninstall, update/reload, and switching between multiple vaults in the same app instance.
4. **Quota, Eviction & OS Storage Pressure:** Resilience against OS-level storage reclamation, particularly iOS Safari/WebKit non-persisted storage eviction rules (e.g. 7-day eviction of unvisited WebViews) and Android low-storage cache purges.
5. **Schema Migrations & Corruption Recovery:** Structured versioning and deterministic recovery/rebuild mechanics if the local database becomes corrupted.
6. **Cleanup Guarantees:** Reliable detection and pruning of orphaned records (e.g. notes renamed or deleted while the plugin was disabled).
7. **Obsidian Plugin API Compliance:** Full compliance with official Obsidian plugin developer guidelines and community review standards.
8. **Performance with High-Dimensional Vectors:** Asynchronous, non-blocking storage and retrieval of typed arrays (`Float32Array`) without causing UI thread latency.

### 9.2 Local Connectivity Options for Desktop Ollama
Evaluating user connectivity options when mobile Companion needs to query desktop Ollama (e.g. manual LAN IP entry, mDNS `.local` hostnames, Tailscale/VPN).

### 9.3 Additional Manifest Fields
Evaluating whether `distanceMetric` or `inputVersion` are required in `.lina/index/manifest.json` for Phase 0.3.x or remain internal defaults.

## 10. Future Acceptance Criteria (Phases 0.3.x & 0.4.x)

- [ ] `.lina/index/manifest.json` records complete vector contract metadata (`provider`, `model`, `dimensions`, `prefixMode`) and `exclusionPolicyHash`.
- [ ] Companion Settings UI locks embedding provider and model to values inherited from published artifacts.
- [ ] If inherited provider is unreachable on Companion, semantic search is safely suspended with an informative message while local text search remains available.
- [ ] Unit tests verify that zero silent fallback to incompatible models can occur.
- [ ] AI Note Analysis provider settings operate 100% independently of the vector embedding contract.
- [ ] Temporary Companion overlay embeddings are stored in persistent, unsynchronized device-local storage and never modify canonical `.lina/index/` files.
- [ ] Equivalence recognition requires all 5 conditions (§5.2), including complete chunk vector coverage and exact exclusion-policy fingerprint verification; time-based deletion and revision-only comparisons (`policyRevision >= cachedPolicyRevision`) are strictly prohibited.
- [ ] Exclusion policy re-evaluation at query/reconciliation time purges excluded notes promptly regardless of generation ordering.
- [ ] Device-local storage mechanism is validated via technical spike covering WebViews, namespace isolation, quotas/eviction, and lifecycle across Desktop, Android, and iOS.
- [ ] Synchronization handshake verifies manifest shape, file presence, counts, digests, and metadata-vector agreement before canonical vectors are marked valid.
- [ ] Idempotent cleanup guarantees that interrupted operations never delete valid temporary entries before canonical vectors are confirmed.
- [ ] Cache reconciliation covers all 6 test cases (§7) with zero duplicate search results.
